## 问题 1:star 数最高、最活跃的开源摄影水印项目是哪些?它们有哪些光印没有的布局、功能或工程做法?

### Takeaway
头部只有两个千星项目——**semi-utils(★1865,Python + Flask 本地网页 UI,模板 = JSON + Jinja2 表达式)** 和 **壹印 yiyin(★1730,Electron 桌面)**,其后是 Copicseal(★326,Electron)、无忧相机水印(★172,纯网页 + Docker)、EXIF Frame(★121,网页 + 已上架 iOS/Android);**原生 Android 的开源同类几乎空白**(Emblematix ★47 且 2025-02 后停更),光印在"开源 + 原生 Android + RAW/广色域"这个组合上没有直接对手。它们比光印强的地方集中在:**配置文件化/可编程模板、免安装网页版与 Docker 自部署、桌面端大屏预览与撤销重做、模板数量(小项目已做到 90–106 套)、GPS 地点、社交平台尺寸预设、拼图切图**。

#### 1.2 光印没有、而这些项目已有的工程做法

- **配置文件化 + 表达式模板**:semi-utils 的模板是一份 JSON,文字字段是 Jinja2 表达式,可写回退链与过滤器,例如 `{{exif.FocalLengthIn35mmFormat|replace(' ','')|default('-')}} f/{{exif.AperatureValue or exif.FNumber|default('-')}}`,Logo 用 `{{auto_logo()}}`,布局由 `processor_name`(`watermark` / `rich_text` / `multi_rich_text`)指定 — [standard1.json](https://github.com/leslievan/semi-utils/blob/main/static/standard1.json)
- **本地 Web UI + REST 接口**:semi-utils 的 `app.py` 是 Flask 服务,暴露 `/api/v1/config`、`/api/v1/file/tree`、`/api/v1/start_process`、`/api/v1/template(s)`,启动后自动打开浏览器,并用 ThreadPoolExecutor 并发处理 — [app.py](https://github.com/leslievan/semi-utils/blob/main/app.py)
- **pip 安装的 CLI**:`pip install exif-frame` 后直接 `frame [-h] photographs ...`,`-q 95` 调质量 — [ppl42/exif-frame](https://github.com/ppl42/exif-frame)
- **免安装网页版 + Docker 自部署**:无忧相机水印提供两个在线地址,并给出 `docker build` / `docker run -p 8088:8088` 步骤;README 强调"无服务,本地处理" — [camera-watermark](https://github.com/dearDreamWeb/camera-watermark)
- **PWA 离线 + 一键部署**:EZMark 支持 PWA 离线使用和 Vercel 一键部署 — [EZMark](https://github.com/LavaCxx/EZMark)
- **一套 Web 代码同时上 iOS / Android 商店**:EXIF Frame README 直接挂 Google Play 与 App Store 徽章 — [exif-frame](https://github.com/jeonghyeon-net/exif-frame)
- **Flutter 多端**:imgFrame 验证了 Android / Windows / Web 三端 Release 构建,Android 端用原生 MediaStore 通道保存 — [imgFrame](https://github.com/PatTianFang/imgFrame)
- **桌面端自动更新**:Copicseal 依赖 `electron-updater`;FrameLab 自述"更新包经签名校验" — [copicseal package.json](https://github.com/copicseal/copicseal/blob/main/package.json)、[FrameLab](https://github.com/yuhaowang774/FrameLabdesktop)
- **导出元数据可选保留**:Copicseal v0.3.7(2025-11-24)加入"导出图片可保留 EXIF 元数据" — [copicseal releases](https://github.com/copicseal/copicseal/releases)
- **GPS 地点**:semi-utils 的 build1521 版本说明为"可选 GPS 位置信息(部分设备可用)" — [semi-utils releases](https://github.com/leslievan/semi-utils/releases);imgFrame 读取 GPS 并可显示"位置"字段 — [imgFrame](https://github.com/PatTianFang/imgFrame);[Shawbbb/Exifreader](https://github.com/Shawbbb/Exifreader) 的仓库描述写明"支持 GPS 反向解析"(★0,仅据描述,未读代码)
- **社交平台尺寸**:Copicseal 的"输出支持快捷选择发布平台模板"需求已关闭 — [copicseal #21](https://github.com/copicseal/copicseal/issues/21)
- **内嵌式(不扩边)与扩展式水印并存**:[copicseal #31](https://github.com/copicseal/copicseal/issues/31)(已关闭)
- 没有搜到任何有影响力的 **Lightroom 插件** 形态的开源项目:GitHub 搜索 `lightroom plugin exif border` 返回 0 条;Adobe 生态里只找到 ★6 的 Photoshop 插件和 ★16 的 Figma Widget — [BrettVibe 插件](https://github.com/BrettVibe/Exif-WaterMark-PlugIn-for-Photoshop)、[Figma widget](https://github.com/sonnylazuardi/figma-photo-frame-widget)

#### 1.3 光印反而领先的地方(用于定位)

- semi-utils、壹印都收到"加了 HDR 照片后只能得到 SDR 图"的 issue 且至今未解决(见问题 2),头部项目同样没有 HDR 保留。
- FrameLab 明确写"HEIC / RAW 请先转格式";无忧相机水印声明只处理 JPEG、TIFF 等;imgFrame 只导入 jpg/png/webp、只导出 PNG — [FrameLab](https://github.com/yuhaowang774/FrameLabdesktop)、[camera-watermark](https://github.com/dearDreamWeb/camera-watermark)、[imgFrame](https://github.com/PatTianFang/imgFrame)
- 壹印当前导出固定 JPEG,且中间主图先落一次 JPEG 再合成,"同一像素被 JPEG 编码两次,产生代际损失" — [yiyin #128](https://github.com/ggchivalrous/yiyin/issues/128)
- semi-utils 曾有"加了边框之后图片颜色变浅"的反馈 — [semi-utils #52](https://github.com/leslievan/semi-utils/issues/52)

### Inferences
- 头部两个项目(semi-utils、壹印)都是 2023 年小米徕卡水印走红后出现的桌面工具,star 高但迭代已放缓(semi-utils 最近一次 push 是 2026-01;壹印 Release 页最新为 v1.7.0),用户在 issue 里反复要"手机版",说明**移动端开源位是空的**。
- Copicseal 依赖 puppeteer-in-electron,推测它的模板是 HTML/CSS 渲染后截图成图(这解释了它能做"PS 启动窗"这类复杂版式);这是推测,未读源码确认。
- 2026 年新冒出的小项目把模板数量卷到 90–106 套、并加入拼图/调色/营销名映射,说明"模板少"(光印约 10 个)会很快成为显眼短板;但这些项目 star 个位数,尚未形成实际用户影响。
- 光印已有的"预设导出 ZIP"与 FrameLab 的"模板包导入导出 JSON"、EXIF Frame 的"主题分享"是同一类需求,但光印缺一个像 semi-utils 那样**人可读、可手写、带回退表达式**的文本格式。

## 问题 2:这些项目的 issue/讨论区里,用户反复要求什么功能?

### Takeaway

#### 4.2 第三方保留 Ultra HDR / 动态照片的可行性(Android 官方文档,已打开原页)

- Ultra HDR 文件 = 主图 JPEG + 作为第二张 JPEG 附加的增益图,用 MPF 与 GContainer XMP 关联;增益图元数据在 `hdrgm` 命名空间(`http://ns.adobe.com/hdr-gain-map/1.0/`),`hdrgm:Version`、`GainMapMax`、`HDRCapacityMax` 为必填;不识别该格式的读取器只显示 SDR 主图 — [Ultra HDR Image Format v1.1](https://developer.android.com/media/platform/hdr-image-format)
- 增益图分辨率可与主图不同(官方建议各边 1/4),但"需要与主图相近的宽高比",方向必须与主图一致 — [同上](https://developer.android.com/media/platform/hdr-image-format)
- 为跨平台兼容,官方建议编码时**同时写 Ultra HDR v1 与 ISO 21496-1 两套元数据**;Android 15(API 35)起从 `Bitmap` 编码 JPEG 时系统会同时写两套;AOSP 的 [libultrahdr](https://github.com/google/libultrahdr) 也支持 — [同上,ISO 21496-1 Compatibility](https://developer.android.com/media/platform/hdr-image-format)
- Android 14(API 34)起 `Bitmap.hasGainmap()` 可判断是否带增益图 — [Display Ultra HDR images](https://developer.android.com/media/grow/ultra-hdr/display)
- 官方编辑指引:用 `Bitmap` API 做旋转/裁剪/缩放时增益图会自动同步;但**叠加贴纸、覆盖第二张图、加滤镜**时增益图"原样保留,可能不是你想要的",应 `Bitmap.getGainmap()` 取出 → 修改主图 → 对增益图做对应修改(例如把贴纸所在区域设为中性值 `Color.GRAY`,并按主图与增益图的尺寸比例换算坐标)→ `Bitmap.setGainmap()` 写回 — [Edit Ultra HDR images](https://developer.android.com/media/grow/ultra-hdr/edit)
- Motion Photo 1.0:主图(JPEG/HEIC/AVIF)后追加视频文件;XMP 用 `Camera:MotionPhoto=1`、`MotionPhotoVersion`、`MotionPhotoPresentationTimestampUs` 标识,并用 `Container:Directory` 描述各媒体项的位置;语义为 `MotionPhoto` 的视频项**必须位于文件末尾**;若主图是 Ultra HDR,则必须同时有 `GainMap` 项且**排在视频项之前**;文件名建议以 `MP.jpg` 结尾 — [Motion Photo format 1.0](https://developer.android.com/media/platform/motion-photo-format)
- 开源侧的旁证:OpenMiLEICAWaterMarkCli 自述"Ultra HDR JPEG 仅在独立 Gainmap 平面上实现了 `extend_gainmap()` 同步扩边,未包含 MPF / XMP 双图容器封包" — [README](https://github.com/benbaobaoshigemi/OpenMiLEICAWaterMarkCli);semi-utils、壹印的 HDR 请求仍未解决 — [semi-utils #122](https://github.com/leslievan/semi-utils/issues/122)、[yiyin #100](https://github.com/ggchivalrous/yiyin/issues/100)

### Inferences
- 对"外扩边框"类水印,保留 HDR 的做法在原理上很直接:把增益图按相同比例扩边,边框区域填"无增益"的值,再把 `hdrgm` 元数据原样带过去;文字/Logo 落在边框上而不压在照片上时,不需要处理官方文档提到的"贴纸继承底图亮度"问题。光印若在 Android 14+ 走 `Bitmap.getGainmap()/setGainmap()` + `Bitmap.compress(JPEG)`,理论上不必自己封 MPF 容器(此句为推断:文档明确了 Android 15 编码时会写入两套元数据,但本次未找到"`compress` 一定保留增益图"的逐字表述,需实测)。
- 需要注意的坑:增益图"中性值"并不总是灰色——它取决于 `GainMapMin/Max`(中性 = 增益为 1.0 对应的编码值);当 `GainMapMin=0` 时中性是 0 而非 128。官方示例用 `Color.GRAY` 只是举例,实现时应按元数据计算(推断)。
- 厂商对动态照片水印的实现看起来是"视频部分也烧录水印"(小米原话"动态照片视频部分添加徕卡或胶片水印"),这意味着第三方要做到同等效果,需要对追加的 MP4 逐帧重新编码加框,成本远高于静态图;一个折中是只给封面帧加框、视频原样保留并重写 XMP——但封面与视频画幅不一致,体验是否可接受需验证(推断)。
- 厂商"可逆"大概率依赖保存未加水印的原图或把水印参数写进私有元数据(华为"之前版本拍的/其他途径来的照片不支持"与此吻合);第三方无法复用这套机制,但可以通过"不覆盖原图 + 记录所用预设"做到等价的可重做。

### Gaps

## 问题 6:是否有开源或标准化的"模板描述格式"可供借鉴?

### Takeaway
**没有跨工具通用的标准**,每个项目各用各的;最值得借鉴的是 semi-utils 的"JSON 结构 + Jinja2 表达式字段"(字段回退、过滤器、函数式自动 Logo),其次是 FrameLab 的"单模板/模板包 JSON 导入导出"和 ppl42/exif-frame 的"`config.yaml` + 资源目录"。据逆向仓库描述,小米自己的水印也是"每款一份 config.json + 贴图 + i18n"的数据驱动结构。

### Cited Findings
- semi-utils 模板示例(节选):顶层是一个处理器数组;`"processor_name": "watermark"` 定义底栏,含 `left_top` / `left_bottom` / `right_top` / `right_bottom` 四个文本槽、`right_logo`、`delimiter_color`、`right_alignment`、`color`;每个槽是 `rich_text` 或 `multi_rich_text`(后者由带各自 `color`/`font_path`/`is_bold` 的 `text_segments` 组成);文本是 Jinja2,如时间字段写成 `{{(exif.DateTimeOriginal or exif.CreateDate or exif.DigitalCreationDate ...|default('0'))[:16]}}` — [standard1.json](https://github.com/leslievan/semi-utils/blob/main/static/standard1.json)
- semi-utils 的架构文档把系统拆成 ImageContainer(读写 EXIF 与图像)与 ProcessorComponent(把水印、边框、阴影等处理器串成链) — [semi-utils Wiki](https://github.com/leslievan/semi-utils/wiki)(Wiki 描述的是旧版命令行架构与 `config.yaml`,与当前 main 分支的 Flask + JSON 模板并不完全一致)
- FrameLab:"自定义模板(当前照片实时合成预览、重命名、分类筛选与搜索、**单模板与模板包导入导出 JSON**)",状态由 `frameConfig` 单一数据源驱动 — [FrameLab README](https://github.com/yuhaowang774/FrameLabdesktop)
- ppl42/exif-frame:CLI 帮助直接列出可改文件 `config.yaml`、两个字体、`logo/` 目录、`signature.png` — [ppl42/exif-frame](https://github.com/ppl42/exif-frame)
- EXIF Frame:自定义主题可保存为模板并分享(需求已关闭) — [#278](https://github.com/jeonghyeon-net/exif-frame/issues/278)、[#289](https://github.com/jeonghyeon-net/exif-frame/issues/289);另有"给每个自定义键补说明"的需求 — [#302](https://github.com/jeonghyeon-net/exif-frame/issues/302)
- imgFrame:预览与导出共用 `FrameLayoutMetrics` + `FrameOptions` 一份配置,保证所见即所得 — [imgFrame README](https://github.com/PatTianFang/imgFrame)
- 小米(据逆向仓库自述,非官方):19 套徕卡水印各有 `config.json`、`i18n.json` 与贴图资产;其 SPEC 覆盖坐标系、缩放公式、View 树布局/旋转、字体/字距/阴影、`rect_params` 圆角框、背景/模糊以及"全配置开关" — [OpenMiLEICAWaterMarkCli README](https://github.com/benbaobaoshigemi/OpenMiLEICAWaterMarkCli)
- 调色侧有事实标准可借:清框影把调色预设存成 Lightroom 可读的 `.xmp` — [Qing-Fram-Shadow README](https://github.com/lumos-1s/Qing-Fram-Shadow)
- 用户对"可分享模板"的期待:Logo 商店 [yiyin #36](https://github.com/ggchivalrous/yiyin/issues/36)、自定义模板 [copicseal #73](https://github.com/copicseal/copicseal/issues/73)

### Inferences
- 光印的"预设导出 ZIP"如果内部是一份文档化的 JSON(版式槽位 + 带回退的字段表达式 + 资源引用),就同时满足了三件事:用户手写/AI 生成模板、社区分享(对应"模板社区"缺口)、未来桌面/CLI 端复用同一渲染规范。semi-utils 的槽位式结构简单但只能表达"底栏四角"类版式;光印是图层式编辑,更接近 FrameLab/小米那种"元素树 + 相对坐标"的描述。
- 字段表达式层面,semi-utils 的做法(`a or b or c | default('-')`)直接解决了 issue 里高频的"某些机型字段名不同/缺失"问题,值得在光印的字段绑定里提供等价的回退链。
- 既然无标准,先发布一份带版本号的公开 schema 本身就可能成为小范围事实标准;但这是判断,没有证据表明其他项目会跟进。

### Gaps
- 未读取 Copicseal、壹印的模板/配置内部格式(无法列仓库目录),不确定它们是否有可导出的模板文件。
- 未核实 OpenMiLEICAWaterMarkCli 的 SPEC.md 细节,也无法确认其对小米实现的描述是否准确。
- 未检索到 W3C/ISO 层面针对"照片相框/水印版式"的标准;与之最接近的通用技术(SVG 模板、HTML/CSS 渲染)在这些项目里只有 Copicseal 疑似采用(推测)。
